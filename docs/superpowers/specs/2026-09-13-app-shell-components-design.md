# Component-based app shell refactor

Date: 2026-09-13
Status: Proposed detailed design; awaiting written-spec review

## Objective and agreed constraints

Reorganize `concepts/app-shell.html` into focused, reusable components and page modules so more pages can be added without extending one monolithic file. Preserve the existing UI, UX, content, and supported interactions. The user approved staged CSS/JS extraction followed by component separation, and accepted the recommendation to use a local development server rather than requiring double-click `file://` operation.

Keep plain HTML, CSS, and JavaScript, one shared app shell, the current public `/concepts/app-shell.html` URL, and existing assets. A framework migration, new pages, redesign, backend implementation, and unrelated audit fixes are outside this refactor.

## Evidence from the current implementation

- The document is 1,204,527 bytes and approximately 30,121 lines.
- Two style blocks contain approximately 11,700 lines. The later prototype-control block participates in the cascade and must retain its precedence.
- Two application script blocks contain approximately 14,335 lines; the main block is one large immediately invoked function. Both blocks parse independently as classic scripts.
- Twelve HTML templates define shell and page structures. Other markup is generated by JavaScript; moving it all into HTML files would require behavioral changes rather than mechanical extraction.
- There are 258 event-listener registrations, 486 document queries, and 103 assignments to `innerHTML` in the current source. These counts indicate coupling, not individual defects.
- Initialization clones templates, mounts the shell, binds listeners, initializes data and forms, applies state, then activates content-view deferral. Prototype controls run afterward and restore settings.
- Hidden page views can be detached and retained in a map. Document-global queries cannot reliably find those views.
- Existing inline handlers use explicitly exposed functions such as `window.addItemRow`. Existing global entry points need temporary compatibility during migration.
- CSS contains no relative external `url()` assets requiring rebasing during the initial extraction. Customer image strings are relative to the HTML URL; their document-relative meaning must be preserved.
- The existing `tests/` directory is empty. Browser checks from the preceding audit provide useful scenarios but are not a complete parity suite.
- The earlier invoice-port design intentionally consolidated pages into one shell to stop copied shell markup drifting. Source-file separation must preserve that decision.

## Alternatives and decision

### Recommended: staged extraction, native modules, assembled HTML templates

First move the existing style and script blocks without changing their contents or execution semantics. Establish a parity checkpoint. Then replace the large shared scope incrementally with explicit imports, component ownership, and page modules. Assemble authored HTML fragments before serving/building so initial templates exist before app initialization.

This achieves focused source files without a UI framework and avoids introducing asynchronous template fetching into every page transition. The trade-off is a small local development/build workflow.

### Alternative: only separate CSS and JavaScript

Lowest initial migration risk and no build requirement, but retains a 14,000-line script and mixed responsibilities. Useful as the first checkpoint, insufficient as the final result.

### Alternative: migrate to a UI framework

Provides established component and tooling conventions, but also rewrites DOM ownership, rendering, events, and state behavior. That raises parity risk and is unnecessary for the current goal. Not selected.

## Source organization

```text
concepts/
  app-shell.html                 # Thin source document / template assembly entry
  app/
    main.js                      # Explicit startup orchestration
    core/
      locale.js                  # Translations, formatting, direction
      appearance.js              # Theme, contrast, accent, density settings
      navigation.js              # Page registry and transition coordination
    shell/
      shell.html
      shell.js
      shell.css
      sidebar.js
      topbar.js
    components/
      dialog/                    # Modal behavior, focus management, shared styles
      record-pager/              # Reusable record navigation controls
      data-list/                 # List engine and its cohesive subfeatures
      notifications/             # Notification panel and selection callbacks
      toast/                     # Status feedback
    pages/
      home/
      invoices/
      customers/
      geography/
      email/
    styles/
      tokens.css
      base.css
      app.css                    # Declares stylesheet order
    prototype/
      controls.html
      controls.js
      controls.css
      fixtures/
  assets/                        # Existing assets and URLs retained
scripts/                         # Minimal template assembly and development serving
tests/                           # Behavior and visual parity checks
```

Directories contain only files their responsibility needs. A component with static markup may have HTML/CSS/JS; a behavior-only utility needs only JavaScript. Do not create three empty files per component, one file per tiny helper, or an arbitrary maximum line count.

The shared data-list component is substantial. Keep filtering, column configuration, pagination, chart integration, and view renderers as understandable subfeatures inside that component rather than scattering them across unrelated utilities. Preserve the existing distinct list-pagination and record-pagination semantics.

## Component ownership and interfaces

- **Shell:** Owns the single frame, sidebar, topbar, and content host. Receives navigation callbacks; does not import invoice/customer internals.
- **Navigation:** Owns the current page ID, registered page instances, and ordered transitions. Asks the active page to run its existing leave guard before changing views. Does not introduce URL routing or new browser-history behavior.
- **Page modules:** Own their record state, fields, page-specific dialogs, and rendering. Invoices, customers, geography, email, and home depend on shared facilities rather than importing each other's private state. Cross-page actions go through explicit navigation requests.
- **Data list:** Receives the existing field configuration, rows, saved layout, and action callbacks. Owns its renderers and controls. It does not decide how an invoice is saved or how a customer record is opened.
- **Dialogs:** Share focus trapping, Escape handling, and restoration behavior. Each page owns its dialog content and business actions. Existing specialized interactions remain supported.
- **Locale and appearance:** Own settings and explicit update subscriptions. Components consume current values and update at the same observable points as before.
- **Prototype controls:** Invoke explicit page/settings operations. They must not reach into private variables or assume inactive page DOM is attached.
- **Fixtures:** Hold representative data separately from behavior, retaining current values and persistence keys.

Use explicit imports and small callback/configuration objects. Avoid a global event bus, dependency-injection framework, or a replacement giant shared context containing all mutable application state. Private DOM lookups should be scoped to the component root; document-level listeners are reserved for genuinely global interactions.

## Page lifecycle and startup

Pages expose a small lifecycle sufficient for their actual behavior: initialize once, activate with navigation data, deactivate without discarding retained state, and dispose resources when actually destroyed. Initialization returns/retains the page root, including when that root is detached. A leave check invokes the page's existing unsaved-work policy.

Final startup order:

1. Parse the assembled shell, icon sprite, templates, and overlay markup.
2. Read persisted settings into model state without rendering detached pages.
3. Initialize shared locale, appearance, and feedback facilities.
4. Mount one shell and register page modules.
5. Initialize required page roots before binding their events or applying DOM-dependent state.
6. Activate the existing initial home/launchpad view and synchronize shell controls.
7. Initialize prototype controls against the registered modules and apply supported restored settings.

Keep page instances alive across ordinary navigation where the current implementation retains them. Deactivation closes transient UI and pauses owned observers/timers as appropriate; disposal removes listeners and chart instances. Do not replace all page DOM on every navigation and silently lose focus, input, scroll position, or selection.

The current customer Create-mode reload exception is directly related to this lifecycle. Correcting it is included only to the extent required for safe module initialization/restoration. Record this as an explicit expected difference from the baseline, with a regression test. Other behavioral fixes require separate scope.

## HTML, CSS, and asset handling

- Assemble local, repository-authored HTML fragments at development/build time. Use explicit inclusion paths and fail clearly on missing or cyclic includes. User-entered data is never treated as an include or trusted HTML fragment.
- Dynamic row/field markup may remain in the component's renderer. Preserve escaping and do not replace safe text operations with unsafe HTML insertion to simplify extraction.
- Preserve DOM structure, IDs, classes, ARIA relationships, and the SVG sprite throughout the mechanical stage. Remove inline event handlers only after equivalent component listeners exist and are verified.
- Preserve CSS declaration order first. Grouping CSS by ownership happens later with an explicit loading order; do not sort, deduplicate, rename selectors, add cascade layers, or change specificity during extraction.
- Static component styles load with the initial page to avoid flashes of unstyled content. Preserve prototype-control overrides after application styles.
- Keep DOM-relative image and link resolution stable. If a JavaScript module needs a module-relative resource, declare that deliberately rather than assuming all relative paths change base when JavaScript moves.
- Retain the existing pinned chart dependency and integrity attributes during the parity migration. Loading it on demand is a separate optimization, not a prerequisite for components.

## Development and output

Provide documented `npm run dev`, `npm run build`, and parity-check commands. Prefer a small Node-based template assembly step and static server without adding a UI framework or general-purpose application platform.

The server serves assembled output, preserving `/concepts/app-shell.html` and the project's index/asset links. Build output goes into ignored `dist/`, retains the required relative paths, and can be served as static files. Developers edit source fragments/modules, not generated output. The development workflow rebuilds changed fragments/styles/scripts before reloading or serving the updated result.

Moving deployment to the generated output may require a build/output-directory setting. Document the required setting and validate the local production build. Publishing or changing remote deployment settings is not part of this task.

Double-clicking the source HTML is not an acceptance requirement. Running through the local server is the agreed workflow.

## Migration stages

1. **Baseline:** Capture the original commit/file identity, meaningful interaction checks, screenshots, storage fixtures, and known failures. Keep the baseline immutable and available for comparison.
2. **Mechanical extraction:** Move the two CSS and two JavaScript blocks into external files. Preserve classic-script execution order and global bridges. Verify parity before restructuring.
3. **Shared facilities and lifecycle:** Introduce module startup, explicit settings/state ownership, scoped roots, and navigation coordination. Extract shared behaviors with their callers in small working increments.
4. **Page and component ownership:** Move page behavior, shared list subfeatures, fixtures, markup fragments, and styles into their final homes. Migrate inline handlers, then remove unused temporary global bridges only after checking consumers.
5. **Final verification and handoff:** Run the agreed browser comparisons against served build output, document expected differences and known defects, and provide a short guide for adding a page through the shared shell.

Each stage must leave a runnable application. Source extraction is a checkpoint, not permission to finish with a monolithic application script under a new filename.

## Verification and acceptance

Use automated browser checks for behavioral parity and deterministic screenshots for visual parity. Exercise the same data, storage state, viewport, theme, and locale on baseline and refactored versions. Wait for real readiness; control animations, skeletons, clock-dependent text, and fixture state consistently instead of accepting unstable screenshot differences.

Required coverage:

- Eight primary surfaces: home, invoice list/record, customer list/record, geographical list/record, and email including compose/reply.
- List, Compact, Adaptive, Cards, and invoice Kanban views; filters, sorting, column settings, grouping, selection, pagination, and charts.
- Record create/view/edit states, invoice tabs and calculations, customer tabs and Scroll Navigator, geographical Tree/Flow, and existing save/undo/leave guards.
- Shared navigation, search, notifications, menus, dialogs, print settings, focus restoration, and keyboard shortcuts.
- Desktop, mobile, and coarse-pointer layouts; light/dark/high-contrast themes; LTR/RTL; reduced-motion behavior.
- Persisted preferences, saved list layouts, reloads, repeated page changes, and opening/closing dialogs without duplicate event responses.
- Development serving and production build asset resolution, with no new uncaught exceptions or failed application asset requests.

Keep current audit defects in a baseline ledger rather than silently repairing them or making them acceptable behavior forever. The customer restoration lifecycle correction is the one explicitly allowed behavior correction here. Any additional necessary deviation must be documented with its reason before implementation proceeds with that deviation.

Acceptance requires unchanged stable rendered appearance and supported interactions, except the documented lifecycle correction; focused page/component ownership; no duplicate shell; no residual legacy application monolith; preserved entry URL and storage keys; successful relevant checks; and clear run/build/add-a-page documentation. Do not invent a screenshot mismatch tolerance to hide unexplained differences.

## Spec review

The design covers architecture, ownership, initialization, templates, CSS precedence, assets, error handling, migration, and validation. It distinguishes the source-file refactor from the previous functional audit and makes the directly related lifecycle exception explicit. The final implementation plan must convert these stages into concrete, independently verifiable changes after user review of this specification.
