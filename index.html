How to read the prototype

It fills the window like a real application — the top bar stays put, the record navigator sits at the bottom, and the form scrolls between them. A dark Prototype controls panel floats in the corner: drag it by its header, collapse it, or hide it entirely. It is not part of the design; it is there so you can put the shell into any state without a backend. About inside that panel explains what you're looking at.

  • ModeCreating a new invoice, working on a saved one, or reading a locked one.
  • StatusOpen, Pending, Posted, Returned, Canceled, Deactivated — the product's real flags.
  • PaymentCredit or cash. Receipt Voucher depends on this, not on status.
  • FailTick it, then post an invoice, to see the failure path.
  • ⌘KShortcuts are wired for real. Press F1 inside the prototype for the list.

The app shell

Twelve iterations narrowed this down to the Record Navigator layout. Earlier versions and the three runner-up layouts (Command Row, Object Header, Context Panel) are no longer kept here — this is the base going forward.

    Record Navigator — working, failing, empty current

    Identity and status own the page header, the four real menus sit on their own row, and record navigation anchors the bottom next to the documents you can generate. Save, posting, cancellation and printing take time and can fail — including the unbalanced journal entry, a real state in the product. Empty states, wired keyboard shortcuts, focus trapped in every overlay, and the print count in the header. The Sales Invoice List (Data Grid, Command List, Grouped Review Board) and Record (Guided Tabs, Single Flow, Split View) views — each with three switchable concepts and, on the Record side, a Simple/Advanced mode toggle — live inside this same prototype, reachable from the sidebar's "Sales Invoice" nav item using the shell's real header, footer and chrome throughout.
